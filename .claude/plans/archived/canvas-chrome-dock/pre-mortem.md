# Pre-mortem — canvas chrome dock

**Bottom line:** proceed with revisions

the expansion from "five debug panels" to "every pill and panel in the bottom chrome" doubles the surface area in a way that exposes one critical contract the plan elides (what `register(...)` actually accepts — component? snippet? render-function? this drives every later phase) and one real-world layout conflict the non-goals dismiss too quickly (`Inspector` in sheet mode lives at `bottom-0 inset-x-0` and already carries `data-canvas-chrome`, so a bottom-left dock will overlap it on mobile). also the debug menu is registered as a dock anchor (via CSS-var bridge) but is *not itself* migrated into the dock — leaving a hybrid where the debug-toggle pill lives in the dock and clicking it opens an external panel that the dock has to measure-around. fold these into phase 0 and the rest of the ordering holds.

### Risks

- [high] integration — the registry's `register(id, item)` contract never specifies whether `item.render` is a svelte snippet, a component reference, or a render function. each of the five things to migrate (`SaveStatusPill` component + props, stats pill with relative-anchored popover, debug-icon button, debug-timings inline div, debug panels with internal `$state`) has different needs; picking the wrong shape forces a rewrite mid-phase. probe: phase 0 must spike `register(...)` against (a) `SaveStatusPill` (rich-prop component), (b) layout-metrics panel (component with internal `$state`), and (c) a one-line debug timings inline div, before picking the contract. write the worst one first; if it doesn't fit, the contract is wrong.
- [high] premise — `SaveStatusPill` is rendered for every user on every paint; a registry that mounts/unmounts on hot-reload or hydration churn would visibly flash the save status, which is exactly the chrome users watch most carefully. probe: phase 0 e2e must include "rapid hot reload simulation" (toggle a layer 10× in a tight loop) and assert `[data-testid=save-status-pill]` is continuously visible — never absent for a frame.
- [high] scope — the stats pill's popover at App.svelte:2211-2258 uses `absolute bottom-full left-0` and *requires* its immediate ancestor to be `position: relative` (provided by `<div class="relative pointer-events-auto">` at App.svelte:2184). if the dock wraps registered items in a flex container without that relative wrapper, the popover anchors to the wrong element and appears at the wrong place. probe: phase 1 must explicitly preserve a `position: relative` wrapper for any registration whose render snippet uses `absolute` positioning; add an e2e asserting the popover's bbox is directly above the trigger pill (not arbitrarily placed).
- [high] integration — `Inspector` in sheet mode is at `bottom-0 inset-x-0` with `data-canvas-chrome` ([Inspector.svelte:299-302](../../../apps/web/src/lib/components/inspector/Inspector.svelte#L299-L302)) — full-width strip across the bottom of the canvas. a bottom-left dock will be *underneath* or *overlapping* the sheet inspector on mobile. the plan declares Inspector out of scope but never resolves the collision. probe: phase 0 must render an e2e at 600×900 (sheet-mode-eligible width) with sheet inspector open, assert no docked item overlaps the inspector's bbox — either by lifting the dock above `isSheet` height (treating the inspector as a `data-canvas-chrome` source the dock anchors above) or by hiding the dock when sheet inspector is open.
- [high] premise — the plan registers `debug-toggle` (the bug-icon pill) in the dock but leaves the debug menu it opens *outside* the dock at App.svelte:2294. clicking the pill opens a panel the dock doesn't know about, and the dock has to use a CSS-var bridge to measure around it. this asymmetry will get worse if a future engine adds its own menu. probe: phase 0 should explicitly decide whether the debug menu is a future dock item (`kind: "panel"`, priority `300`, large body) or whether it stays an unmanaged sibling forever. if the answer is "future dock item", file the deferred work in `bugs.md` so it doesn't surprise phase 5; if "unmanaged", the CSS-var bridge is permanent infrastructure, not a scaffolding hack.
- [medium] scope — `BackButton` at top-left is declared out of scope but is `position: absolute top-3 left-3 z-30` with no `data-canvas-chrome`. when a top-left dock is later mounted, `BackButton` will conflict with it unless retroactively docked. accepted today but worth flagging: the dock's top-left corner stays unmounted in this plan; the first non-debug user of top-left will trigger a small re-think. probe: confirm in phase 0 that only the bottom-left corner mounts in this plan; if any item registers for `tl`, fail loudly so it's caught at code review.
- [medium] scope — phase 1's "dismantle the bottom-bar wrapper" silently changes a subtle behaviour: today, when `readOnly && !statsPillVisible && debugPillHidden`, the wrapper doesn't render at all and the corner has zero chrome inset. with the dock, the container element always exists; if it carries `data-canvas-chrome` even when empty, `measureCanvasChromeInsets` returns a non-zero inset for an invisible element. probe: phase 1 e2e must assert that when all items in a corner are guard-hidden, `measureCanvasChromeInsets` for that corner returns zero (either dock un-mounts when empty, or omits the chrome attribute, or has zero width/height).
- [medium] expertise — `$state`-backed module-level registry (`dockRegistry.svelte.ts`) is project-new for the dock pattern; svelte 5 + rune-based stores at module scope have HMR and SSR caveats. test isolation (one test affecting registry state read by the next) is a real risk. probe: phase 0 must add a teardown that asserts `dockRegistry` is empty after a test; if not, switch to a context-provided registry instead of module-global state.
- [medium] performance — the priority-space convention (0-99 status, 100-199 tools, 200-299 debug) is documented but not enforced. nothing prevents a future contributor from registering at priority `1000` or duplicating `10`. low-stakes today, drift-prone over time. probe: phase 5 should add a lint-style check or a runtime warning when a registration uses a priority outside the documented ranges; defer if the project has no existing lint-rule infrastructure.
- [medium] operational — `pnpm verify` covers lint+typecheck+unit+e2e, but the plan calls for "visual snapshots" in phases 1, 2, 5. if `tests/e2e/visual-*.spec.ts` is not currently part of `pnpm verify` (or runs in a separate suite), regressions only surface manually. probe: phase 0 must confirm whether visual snapshot tests are part of `pnpm verify`; if not, the plan must say "visual snapshot is a manual review step" and stop pretending automation catches it.
- [low] dependency — none; pure svelte/css.
- [low] performance — `dockRegistry` is a `$state` map iterated on every paint of the dock; with ≤ 10 items per corner this is trivial. flag only if registered items balloon.
- [low] integration — z-index ordering: today's bottom-bar is `z-30`, debug menu `z-40`. the dock subsumes both; if the dock container chooses one z-index, pop-overs from registered items that rely on a higher stacking context may collide. probe: keep `z-30` on the dock outer container; per-item popovers manage their own stacking inside their render snippet.

### Walking-skeleton check

phase 0 ships one always-visible pill (`SaveStatusPill`) and one user-toggled panel (layout-metrics) through the new registry + dock, with the chrome-inset contract verified. that is the correct shape *provided* phase 0 also spikes the `register(...)` contract against the three hardest item shapes (rich-prop component, internal-state panel, inline div) — picking the contract from one example will guarantee a rewrite when the second migration starts. fold the three-shape spike into phase 0 DoD.

every later phase still replaces a stub (phase 1 replaces hand-coded pill mount points with registrations; phase 2 replaces the rectangular collapsed header with a pill; phase 3 replaces the four remaining hardcoded family-view debug panels; phase 4 replaces "open everything overflows" with "auto-collapse"; phase 5 replaces ad-hoc styling with theme tokens). that part is sound.

the missing layer in phase 0 is the **`Inspector` sheet-mode collision** — a runtime mode (`isSheet`) the dock has to coexist with. it isn't a "phase 0 stub" exactly, but ignoring it until phase 4 (overflow handling) means the first mobile user opens the inspector and the dock disappears under it. add a sheet-mode e2e to phase 0 DoD.

### Phase-order revisions

| original | proposed | reason |
|---|---|---|
| phase 0: dock + 1 pill + 1 panel + chrome-inset | phase 0: dock + 3-shape `register(...)` spike + 1 pill + 1 panel + chrome-inset + sheet-mode-inspector e2e + debug-menu-future decision | high-severity integration risks (registry contract, sheet inspector overlap, debug-menu asymmetry) all become cheap if surfaced in phase 0; defer any and a later phase forces a rewrite |
| phase 1: migrate all bottom-bar pills | phase 1: migrate stats pill **first** (proves popover-anchoring contract), then debug-icon, then debug-timings | high-severity scope risk on the popover-anchor — proving it on the trickiest pill first ensures the snippet wrapper convention is correct before two more pills depend on it |
| phase 3: badge salience decision recorded before code | (unchanged, already correctly ordered) | — |

no other reordering. risk concentrates in phase 0 (registry shape, inspector collision, debug-menu boundary) and phase 1 (popover anchoring); both are addressed in place.
