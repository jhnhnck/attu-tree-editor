# pre-mortem — migrate debug menu into dock

**bottom line:** proceed with revisions. three high-severity geometry / lifecycle risks need folding into phase 0 DoD before code lands; merge phase 1 into phase 0 (the bridge becomes dead code on registration with zero external consumers). No phase reordering beyond the merge.

---

## risks

- **[high] premise / verification — wedged-spec evidence vs. fix.** the three wedged e2e specs (`family-view-debug-coi.spec.ts`, `family-view-debug-navigation.spec.ts`) never explicitly open the inspector sheet; selection of Inga via palette + Enter at Pixel-7 width auto-opens it (`Inspector.svelte:204` `isSheet = mql.matches`, default-`true` on narrow). The wedge is at `getByTestId("debug-panel")` interaction, not at sheet inspector itself. sheet inspector is `z-50`; today menu is `z-40` (below sheet, so sheet covers it = pointer intercept). After migration, the menu lives inside the dock at `z-30` — further below sheet. The plan trusts the dock's `--inspector-sheet-height` anchor to lift the menu's geometry above the sheet bbox, so z-order won't matter. But if the dock's anchor clamp keeps the dock fixed to host-top (per phase-5 clamp at `host.top + 8px`), and the menu height alone (~732px) plus the sheet height (~686px on Pixel 7 ≈ 75% of 915 viewport) exceeds `host.height` (≈ 879px), the dock falls into `overflow-y: auto` mode and the menu's toggle buttons end up inside a clipped scroll container — visible only by scrolling the dock. e2e `.click()` works on offscreen elements via auto-scroll, but the hand-test on real Pixel 7 may feel awful. **probe:** before phase 0 code lands, manually measure `host.height` and `cap` on Pixel 7 with sheet open; verify the projected menu+pills stack fits without `overflow-y: auto`. If it doesn't, raise the question whether menu needs its own narrower height cap inside the dock (e.g. `max-h-[60vh]` or `max-h-[calc(100vh-var(--inspector-sheet-height,0px)-8rem)]`) rather than the inherited `max-h-[80vh]`.

- **[high] integration / lifecycle — inert bridge is one refactor mistake from double-counting.** the css-var bridge `$effect` at `App.svelte:273-292` is left "inert" by removing `bind:this={debugMenuEl}`. The plan says "the `$effect` early-returns when `debugMenuEl` is undefined". That is correct as written — line 274 has `!debugMenuEl` in the guard. But the effect's dep set includes `debugOpen` and `debugMenuEl`, both `$state`. If phase 0 forgets to drop `bind:this` (or wires it inside the snippet body by accident — snippets run inside the dock so `getBoundingClientRect()` would return the menu's position-inside-the-dock-flex frame), the `update()` callback writes `--debug-menu-bottom = host.bottom - menu.bottom` against the dock-anchored menu rect, which is *not* zero — typically positive but small — and the dock's `bottom:` calc then re-adds menu-height *on top of* the dock's own measured anchor, double-counting and pushing the dock further up the host every render. **probe:** add a phase-0 assertion that after `debugOpen = true` and `flushSync()`, `--debug-menu-bottom` is not set on the canvas-host (or alternatively, delete the bridge code in phase 0 alongside the registration — splitting into phase 1 buys nothing and adds a risk).

- **[high] integration — `forceCollapsible: false` interaction with `measureAndForceCollapse`.** `CanvasChromeDock.svelte:183` `project()` at line 212 iterates *all* items and uses `measured` height (not `PILL_PX`) for any item not in the forced set. The menu with `forceCollapsible: false` will never enter the forced set, so its full natural height always counts toward `naturalHeight` and `finalProjected`. That's correct in spirit — the menu must stay expanded — but means: (a) `cap` is computed from `dockRect.bottom - hostRect.top` *before* the menu renders inside the dock; once the menu inflates the dock, `cap` is stale until next rAF. (b) the force-collapse walk now force-collapses every family-view panel (200, 210, 220, 225, 230) into pills whenever the menu alone exceeds `cap - menu - gap`, even on viewports where the menu+one-panel-expanded would fit fine. Less surface area for the user to expand panels intentionally. **probe:** at 1440×900 (desktop), open the menu plus the layout-metrics panel manually-expanded; observe whether the layout-metrics panel force-collapses to pill only because the menu is open. If yes, the priority story changes: menu-open implicitly demotes every debug panel below the priority-300 threshold. Record whether this is desired UX or a regression vs today's behaviour (today the menu and the panels are independent floaters that overlap freely).

- **[medium] integration — `max-h-[80vh]` inside the dock's `flex-col-reverse` column.** Today the menu is `position: absolute` with a fixed containing block (the canvas-host) — `80vh` resolves against the viewport. Tomorrow the menu is a flex item in the dock; `vh` units always resolve against the viewport regardless of containing-block, so the number stays 80vh ≈ 732px on Pixel 7. But the dock's flex item has no explicit `flex-basis`, so the item's actual height is min(content, max-height, available-flex-space). With `flex-col-reverse` and the dock's own `overflow-y: auto` fallback wrapping the column, the menu's `max-height: 80vh` is the binding constraint only when the menu's content exceeds 80vh. The menu currently scrolls inside itself via `overflow-y-auto`. Net effect: works, but you can produce a double-scrollbar (dock scrolls + menu scrolls) on extreme mobile. Cosmetic, not functional. **probe:** Pixel 7 with sheet open + menu open + every debug toggle on — does the user see two nested scroll surfaces? if so, drop `max-h-[80vh] overflow-y-auto` from the menu when registered as a dock item, and rely solely on the dock's overflow fallback.

- **[medium] lifecycle — `DockRegistration`'s prop-update `$effect`.** The render snippet `render={debugMenuPanel}` is a snippet reference; svelte 5 re-creates the snippet closure on each parent rerender if it's defined inline at the use site. The pattern in `FamilyViewDebugOverlay.svelte:1456` declares `{#snippet layoutMetricsPanel(ctx)}` at template top-level, so the snippet reference is stable. The plan says "wrap the menu's content … in a `{#snippet debugMenuPanel(_ctx)}` template" — svelte snippets are compiled to stable identifiers, not re-allocated, so `updateItem(id, { render })` won't fire on every render. **Caveat:** the phase-0 click-handler bug in the parent plan was exactly this kind of effect-loop. **probe:** add a phase-0 DoD line: with debug menu mounted, the registry's internal items map mutation count after page settle is ≤ 1 per registration (one initial register, one mount-only updateItem). Read `window.__treeDebug` or instrument the registry temporarily. If > 1, the snippet identity is changing across renders and the menu re-registers on every keystroke inside its textarea.

- **[medium] premise — priority 300 stack arithmetic on Pixel 7.** layout-metrics is 230 and renders below the menu. With both expanded, stack = 4 pills (28px ea) + 3 gaps + layout-metrics (~200px) + 1 gap + menu (~732px) ≈ 992px on Pixel 7 (915px viewport). Dock anchors to `host.top + 8`; effective cap is ~879px. Exceeds cap by ~113px before any other debug panel. Force-collapse walks panels 200→210→220→225→230, demoting all five to pills. Stack now = 4 user pills + 5 panel pills + menu = 9×28 + 8×8 + 732 = 1048px. Still > cap. Falls into `overflow-y: auto`. So on Pixel 7 with menu open, the guaranteed state is "dock is a scrollable column with menu at top and 9 pills below". The user has to scroll within the dock to reach any debug toggle button. This is the fix for the bug (the buttons are reachable), but the UX is "scroll-in-overlay-on-top-of-scroll-sheet-inspector". Worth recording as the accepted resolution explicitly. **probe:** manually validate on Pixel 7 hardware (or chromium device-emulation) before phase 0 ships. If the experience reads as broken, the menu needs its own height cap (e.g. `max-h-[calc(100vh-var(--inspector-sheet-height,0px)-12rem)]`).

- **[medium] integration — `data-canvas-chrome` removal from the menu div.** Today the menu's own `data-canvas-chrome` causes `measureCanvasChromeInsets` to add the menu's bbox to chrome-inset bottom. After migration, only the dock carries `data-canvas-chrome`; the dock's bbox already grows to include the menu (it's a flex child), so the inset reading remains correct. **BUT** `fitMath.ts:131` walks `scope.querySelectorAll([data-canvas-chrome])` and computes per-element penetration. With one carrier (the dock) vs two (dock + menu), the math is not identical — today the menu and the (then-separate-floating) menu's bbox each contributed; now the dock contains the menu so only one rect is measured. The plan claims "within ±2px"; in practice the dock's bbox tightly encloses the menu so the bottom-inset numbers should match within sub-pixel rounding, but the priority math in `fitMath` (line 173, anchor-side selection, line 174 charge `min(vertical, horizontal)`) takes only the smaller of the rect's vertical or horizontal extent. The dock is now ~290px tall × ~75px wide → charged 75 horizontal to left. Today the menu's standalone rect is ~732 tall × ~290 wide → charged 290 left. The bottom inset doesn't change but the left inset does, and `fitToView` may shift left-pan accordingly. **probe:** add a phase-0 e2e that compares `measureCanvasChromeInsets` for every edge (top, right, bottom, left) before/after the migration, not just bottom. If left-inset shifts > 5px, audit `fitToView` consumers.

- **[medium] lifecycle — registration gate `{#if debugOpen}` rapid-toggle race.** Today opening the menu mounts a DOM div. After migration, opening the menu mounts a `<DockRegistration>` which fires the `$effect` once, calling `register()` and `updateItem()`. `register()` throws on duplicate id (`dockRegistry.svelte.ts:60`). If the gate flickers (e.g. `debugOpen = false; debugOpen = true` within one tick via a keyboard handler), Svelte may or may not destroy + recreate the `DockRegistration` instance in the same microtask. If those microtasks reorder, we get a "duplicate id" throw. Today the failure mode is "menu flashes"; tomorrow it's a hard throw that leaves the registry in a broken state. The phase 0 fix used `untrack` to prevent depth-exceeded, not to prevent register-after-register. **probe:** add a phase-0 unit test that rapidly toggles a `{#if guard}<DockRegistration … />{/if}` flag 20× via `flushSync` boundaries and asserts no thrown registry error.

- **[low] scope — phase 1 grep coverage confirmed.** `--debug-menu-bottom` / `--debug-menu-height` / `debugMenuEl` appear only in `App.svelte` and `CanvasChromeDock.svelte`. Grepped `apps/web/tests/` and `apps/server/` for completeness — zero hits. Phase 1 grep is safe.

- **[low] scope — the menu has a `textarea` (line 2624) inside the dump/load section.** Inside the dock's `pointer-events-auto relative` wrapper, the textarea's keyboard focus and pointer events should pass through. No popover / dropdown inside the menu so no internal stacking surprises.

- **[low] expertise — phase 0 `effect_update_depth_exceeded` regression history.** The fix from the parent plan's phase 0 (two effects, both `untrack`, plus `updateItem` for in-place patches) is already in `DockRegistration.svelte:43-58`. New field `forceCollapsible` threads through `Props`, `register({...})`, and `updateItem` patch. As long as the new field is added to the `next` object at line 56 AND the `register({...})` payload at line 44, the same untrack-pair pattern protects it. **Phase 0 DoD does not explicitly call out the line-56 `next` object** — if a code-review misses it, `forceCollapsible` won't propagate on prop change. For the menu it doesn't matter (always `false`, never flips), but a future panel that reads `forceCollapsible` reactively would silently desync. **probe:** phase 0 scope item explicitly lists the three call sites in `DockRegistration.svelte` that need touching: `Props`, `register({...})`, `next` object at line 56.

- **[low] operational — visual snapshots.** Phase 1 DoD says "re-run … `canvas-chrome-dock.spec.ts` (chromium + Pixel 7) and the three previously-wedged specs". No mention of regenerating `visual-canvas-chrome-dock.spec.ts` baselines. The dock now contains the menu, which inflates the bottom-left chrome bbox by ~700px on viewports where the menu used to render separately. Every snapshot that had the menu open will need regeneration; every snapshot that didn't will be unaffected. **probe:** before phase 0 ends, run the visual suite locally and identify which baselines need regenerating. Bake regen into phase 0 DoD.

## definition-of-done additions (folded into plan)

- with `debugOpen === true` and `flushSync()` settled, the canvas-host element exposes neither `--debug-menu-bottom` nor `--debug-menu-height` custom properties (proves the bridge effect is inert, not stale-bound)
- `measureCanvasChromeInsets(canvas-host)` returns values within ±5px per edge (top/right/bottom/left) before vs after the migration, at 1440×900 and 412×915, menu both open and closed
- registry `items` map mutation count after page settle is ≤ 1 per `DockRegistration` instance (catches snippet-identity churn that would re-trigger phase-0 parent-plan's depth-exceeded class of bug)
- rapid-toggle of `debugOpen` (20× via `flushSync` in a unit test) does not throw a "duplicate id" registry error
- at Pixel 7 (412×915) with sheet inspector auto-open from selection + debug menu open, manually confirm whether the user-visible dock is a scrollable column with menu at top and 9 pills below, or whether the menu fits without engaging the dock's `overflow-y: auto` fallback. Record the decision in the plan log before declaring phase 0 done; if the scrollable-column UX is unacceptable, replace the menu's `max-h-[80vh]` with a viewport-aware cap that accounts for sheet inspector height

Record whether this is desired (menu-open implicitly demotes panels) or a regression. If regression, raise menu's priority threshold or rethink force-collapse interplay

- regenerate any `visual-canvas-chrome-dock.spec.ts` baselines that capture the bl corner with menu open (`pnpm -F web exec playwright test visual-canvas-chrome-dock --update-snapshots`); audit the diff to confirm only the bl chrome changed
- grep also `apps/web/tests/` (zero hits confirmed in this pre-mortem) and `apps/server/` (zero hits) — record the result in the closing commit so a future archaeologist sees the bridge had no external consumers

## notes the plan should fold in

- the dock's `data-canvas-host` attribute is load-bearing (parent plan log line 31). The menu's bbox math depends on `inspectorEl.closest("main")?.querySelector("[data-canvas-host]")` resolving to the right element. Migration doesn't move the attribute, so this just needs to not regress.
- accepted-risks #5 (anchoring on small mobile) is real and the math is in the [high] risk above — the menu+panels+pills stack exceeds `cap` on Pixel 7 with sheet open. Phase 4's overflow-y fallback in the parent plan handles it functionally; the UX implications are the only open question. Worth a one-line explicit accept in the plan: "on Pixel 7 with menu open + sheet inspector, the dock engages overflow-y scrolling — this is the fix, and `.click()` auto-scrolls in e2e".
